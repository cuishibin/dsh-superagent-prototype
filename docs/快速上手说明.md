# dsh-superagent 项目快速上手说明

本文档用于帮助你快速理解 `dsh-superagent` 这个仓库的结构、核心运行方式，以及如何把它真正跑起来。

## 1. 项目是什么

`dsh-superagent` 不是一个普通的 Web 应用，也不是单纯的命令行工具，而是一个运行在 `DeepSeek Harness`（简称 `DSH`）中的主动式编码代理插件。

它的核心目标是：

1. 监听 GitHub，按需也可监听飞书。
2. 判断某条消息是否有资格成为一个可执行请求。
3. 把合法请求转成 Ticket。
4. 为每个 Ticket 启动独立的执行 Session 和工作目录。
5. 在原始对话中回传进展、问题和结果，例如评论、回复或 PR。

一句话理解：它是一个“挂在 DSH 里的、面向单个 GitHub 仓库的自动协作代理系统”。

## 2. 先看结论：这个项目怎么跑

这个项目**不是**执行 `pnpm dev` 就能起来的类型。它的运行依赖主要是：

- `Node.js 22.19+` 或 `24+`
- `pnpm`
- `git 2.32+`
- `Python 3.8+`
- `tmux`
- `GitHub CLI (gh)`
- `DeepSeek Harness (dsh)`

此外，它还依赖：

- 一个用于代理执行的 GitHub 账号
- 一个待接管的 GitHub 仓库
- 可选的飞书机器人配置

标准启动路径如下：

```sh
pnpm install
pnpm build
npm install -g @deepseek-ai/dsh@0.2.1-rc.3
dsh superagent --from-default-profile web --dump-config > /dev/null
dsh plugin --profile superagent add "link:$PWD"
```

然后还需要：

1. 配置 `~/.dsh/profiles/superagent/cordis.patch.yml`
2. 配置 GitHub 代理账号的 `gh` 包装器
3. 在面板或 Management API 中写入 Source / Policy / Execution / Prompts 设置
4. 通过脚本启动服务：

```sh
scripts/dsh-superagent start
scripts/dsh-superagent status
```

## 6. `src/` 目录怎么读

### 6.1 最重要的入口

- `src/index.ts`
  - 插件主入口
  - 创建 `Runtime`
  - 把 `dsh-superagent` 挂载到 DSH 中

- `src/app/runtime.ts`
  - 组合根
  - 负责启动、停机、初始化各组件

- `src/core/engine.ts`
  - 领域核心
  - 是 Ticket / Trigger / Decision / Assignment 的唯一写入者

### 6.2 主要模块职责

| 目录 | 作用 |
| --- | --- |
| `src/core/` | 领域模型与核心业务规则，决定 Ticket 如何产生、流转、结束 |
| `src/app/` | 应用层与运行时胶水代码，连接 HTTP、Store、Effects、Sessions、Prompts |
| `src/sources/` | GitHub / 飞书输入源适配层，负责监听、翻译消息、回写通道 |
| `src/executor/` | Worker 执行器，负责每个 Ticket 的独立执行会话与工作目录 |
| `src/client/` | Web 管理面板前端 |
| `src/infra/` | 命令执行、环境隔离、路径、文本、健康检查等基础设施 |

### 6.3 可以这样理解整体链路

从运行机制看，这个项目基本是下面这条链：

`Source(GitHub/飞书) -> Trigger -> Policy/Eval -> Ticket -> Executor -> Reply/PR -> Panel`

更具体一点：

1. `src/sources/` 把 GitHub/飞书事件翻译成 Trigger。
2. `src/core/intake.ts` / `src/core/evals.ts` 判断这些 Trigger 是否值得进入评估。
3. `src/core/tickets.ts` 决定是否创建或恢复 Ticket。
4. `src/executor/dsh.ts` 为 Ticket 分配 DSH Session 和目录。
5. `src/app/outbox.ts` / `src/sources/*-channel.ts` 把结果写回外部平台。
6. `src/client/` 把整个系统的状态展示为面板。

## 9. 真正启动前，你需要知道的几个关键点

### 9.1 这是 DSH 插件，不是独立应用

本项目最终是作为 bundle 挂进 DSH 的。`cordis.patch.yml` 里定义了：

- 主插件 `dsh-superagent`
- GitHub Source 插件 `dsh-superagent-github`
- 可选 Feishu Source 插件 `dsh-superagent-feishu`
- 专用执行器预设 `dsh-superagent-worker`
- 专用主 Session 预设 `dsh-superagent-router`

### 9.2 面板不是单独启动的前端工程

`src/client/` 的前端代码会随着插件一起构建进 `lib/client.js`，由 DSH Web 侧加载，而不是用 `vite dev` 之类单独起服务。

### 9.3 服务启动依赖 profile

真正的服务实例来自 DSH profile，比如文档里默认的 `superagent`。项目脚本 `scripts/dsh-superagent` 负责：

- 启动 profile
- 用 `tmux` 托管进程
- 轮询健康状态
- 判断当前是正常运行、配置缺失还是某个模块报错

### 9.4 配置比代码更关键

第一次跑不起来，最常见原因不是代码，而是配置没补齐：

- GitHub 代理账号没准备好
- `gh-agent` 包装器没登录
- `stateDir` 没配
- 仓库地址没配
- Policy 允许名单为空
- Execution 的 `prepare` 命令没配

## 10. 最短落地路径

如果你的目标是“尽快在本地把它跑通一次”，建议按下面做：

1. 在 Linux/macOS/WSL 准备环境：`node`、`pnpm`、`git`、`python`、`tmux`、`gh`、`dsh`
2. 在仓库根目录执行：

```sh
pnpm install
pnpm build
```

3. 全局安装 DSH：

```sh
npm install -g @deepseek-ai/dsh@0.2.1-rc.3
```

4. 创建 DSH profile 并挂载插件：

```sh
dsh superagent --from-default-profile web --dump-config > /dev/null
dsh plugin --profile superagent add "link:$PWD"
```

5. 复制示例配置并填写占位符：

```sh
cp examples/profile.cordis.patch.yml ~/.dsh/profiles/superagent/cordis.patch.yml
```

6. 按 `docs/006-deployment.md` 配置：
   - GitHub agent 账号
   - `gh-agent`
   - Source
   - Policy
   - Execution
   - Prompts

7. 启动：

```sh
scripts/dsh-superagent start
scripts/dsh-superagent status
```

8. 在允许账号下，到目标仓库评论：

```text
@<agent-login> <你的请求>
```

看到面板里出现 Ticket，就说明主链路通了。

## 11. 我对这个项目的理解摘要

如果你从工程视角快速理解，这个仓库可以分成 4 层：

1. **领域层**：`src/core`
   - 定义 Trigger、Eval、Ticket、Assignment、Decision 的生命周期

2. **运行层**：`src/app` + `src/executor`
   - 负责启动、队列、会话、存储、效果执行、任务调度

3. **接入层**：`src/sources`
   - 负责 GitHub/飞书的输入输出适配

4. **可视化层**：`src/client`
   - 负责运维和人工介入面板

它不是“单次问答式 agent”，而是一个带有：

- 持久化存储
- 多 Ticket 生命周期管理
- Source 监听
- 路由/执行分工
- 面板管理
- 提示词和策略可配置

的长期运行代理系统。
