# 000 理念

`dsh-superagent` 既是一套框架，也是一种与智能体协作的工作方式。它的核心原则是：

**尽可能少占用人的注意力，尽可能多地创造价值。**

项目中的每一部分，都要以它消耗了多少注意力来衡量。一次消息、一次通知、一个问题、一项设置、面板上的一个元素、文档中的一段文字，都会消耗某个人的注意力；如果它带来的价值没有超过这份成本，它就应该被移除。

## 这对智能体意味着什么

- **它只在被请求时行动，或者在已有书面规则允许时行动。** 只有当请求直接指向智能体，并且来自团队允许的人时，这个请求才算数：要么此人在允许名单中，要么他所在的会话已被团队开放为可发起请求的地方。没有人请求的工作，必须有团队写下的规则作为依据，而且一开始只会以“记录如果做会怎么做”的模式运行。
- **它只在必须由人行动、或者结果已经可供人使用时发言。** 它会确认一次请求，并说明自己将做什么。工作过程中保持安静。只有在结果准备好、需要一个决定，或者无法完成时才再次发消息。消息要短，并且发回原始请求所在的会话。
- **它一次只问一个具体问题，** 并且用结构化形式提出，这样问题能真正到达人，而不会淹没在一长段报告里。
- **它按影响停下，而不是按投入停下。** 一个局部修改会推进到“足以被评审”的结果为止。需要设计决策的改动，则会在清晰问题处停下。
- **它要如实汇报。** 草稿要明确标注为未完成，失败就按失败汇报，绝不能为了避免提问而绕过限制。

## 这对设计意味着什么

- **概念要少。** 设计中只保留领域本身需要的概念，比如 Source，以及它们的具体实现，比如 GitHub 和飞书。一个业务需求，要么成为这些概念中的某个属性，要么成为智能体遵循的一段提示词，而不是再额外引入一个新概念。
- **设置要少。** 如果某个默认值几乎适合所有团队，就应该用默认值替代设置项。团队可以用文字描述的行为，应当写进提示词，而不是做成设置。
- **面板只显示真正需要人的事情。** 它首先列出那些正在等待人的事项。系统健康时，不应占用额外空间。
- **文档按顺序阅读。** 每一篇编号文档都只建立在前面的文档之上，这样读者永远不会遇到一个尚未被引入的概念。

## 责任

这个智能体会使用你们团队每天都能看到的账号去评论、开 Pull Request、给人发消息。它发出的每一条消息，都会消耗你同事的注意力，而你需要为这些消息负责。智能体能力越强，操作它的人对团队就越需要谨慎：

- **从小范围开始。** 一开始只放很短的允许名单，并且让主动工作只做记录。等到“它本来会怎么做”看起来已经合理，再逐步放开。
- **把调优目标放在更少噪声上。** 如果智能体太吵，就让提示词更短、更严格，或者直接暂停它。不要靠再发更多解释消息来解释这些噪声。
- **不要拿它来制造数量。** 批量 PR、广播式消息和形式主义工作，带给团队的成本通常大于收益。
- **对它说的话负责。** 读一读它以你的名义发出的内容；如果它说错了，就在提示词里纠正，而不是放任不管。

目标是在正确的时刻给出恰到好处的帮助，而在其他任何时候都保持安静。
